Findings (no code changed)
1. fn_8009F4D8 (qsort comparator): the EA bug is CONFIRMED in the original asm. After stwu r1,-0x10 it loads 0x2C(r1)/0x30(r1), which are &pA+0x24 and &pB+0x24, i.e. words of qsort's own frame. It does this before it even stores r3/r4. So fn_8009F0F0's sort order is arbitrary. The existing EA bug comment stays. Its first line now says the order was "meant as" newest first.
2. fn_8009E604 never uses pBackupName, and no GameCube code ever creates BU_BASLUS-20757 (MC.c passes MC_BACKUP_NAME five times, always to this unused parameter). Knock-on effects: fn_8009D3DC returns 1 ("one directory entry needed") for every readable card, even when the save exists. fn_8009D1D8's backup check is dead. fn_8009ED34 and fn_8009EC30 also ignore their name parameters (hard-coded MC_FILE_NAME/MC_BACKUP_NAME via fn_8009EF68).
3. fn_8009ED34 loads the main file and then the backup into the same first image. With a backup on the card, a good main returns 0 but leaves the BACKUP's bytes in lbl_80281FE8 (and then deletes the backup). This is latent, because of finding 2. The comment now says so.
4. fn_8009F6A0 looks for "BASLUS-20572", while the unit's own names use "BASLUS-20757". The string is in the original .data (MC_Gc.s), so it is EA's data, not our typo. Its only path is MC.c fn_800A2194 -> FE_MessageTable:4300, a yes/no for the menus. It is probably another title's save; which one is unproven.
5. Files left open on error paths: fn_8009DD94 (the unknown-result default and a failing fn_8009E280 return without fn_8009D010), fn_8009E604 (a failing fn_8009E47C), and fn_8009F514 (the created "EASB" file is never closed; it also sets attributes and lbl_802813D8 from an uninitialised file.fileNo when the create fails).
6. Cards left mounted: fn_8009D1D8 (every return after its own mount except the both-files-present one, which never happens per finding 2), fn_8009D3DC (the return-1 paths), fn_8009D50C ("EASB" missing), fn_8009EE28 (fn_8009F734 failure; its comment says so). Separately, in fn_8009D74C a check/encoding/free-blocks failure after a successful CARDMountAsync returns without setting MC_CARD_MOUNTED, so fn_8009DBAC never calls CARDUnmount for that channel.
7. Card-table reads at [-1][-1] before the -1 check: fn_8009D1D8, fn_8009D3DC, fn_8009D50C. The EA bug comment is right: it reads -0x130 bytes, which lands inside lbl_801F1110 (the CRC table). It is harmless, because the value is not used before the -1/-1 return.
8. Split question (do not move code): fn_8009F780 (GX vertex format 2: POS xyz f32, CLR0 RGBA8, TEX0 st f32) and the empty fn_8009F7E4 are shader code. Their only callers are GoShaderObject_PrelitUVAnimation_Gc fn_800716D4/fn_800716FC. But they sit INSIDE MC_Gc's .text (0x8009CB9C-0x8009F850), between fn_8009F734 and the card-state getters fn_8009F7E8/F7F4/F834. Moving them would need MC_Gc cut into three units, so EA's MC_Gc.c most likely really held them.
