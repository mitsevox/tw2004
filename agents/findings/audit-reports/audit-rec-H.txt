Findings (no code changed)
1. fn_8008B820 and fn_8008B760: CONFIRMED identical bodies (next=1, abort, run until state 1). B820's only caller is fn_8008B00C (shutdown). B760's callers are GoEntry.c:114 (entering the front end) and DiscCheck.c:124 (game type 3, then fn_8008B978(1) pauses the machine). Two EA copies. Any names should keep them apart by caller, not merge them.
2. CRAP_NUM_GOLFERS is 1 (camera.h:504): CONFIRMED. The ring links slot 0 to itself, so these are dead in effect: the next/prev branches of fn_8008B044 and fn_8008B20C, fn_8008DCF0 (always 0, since every pGolfer is slot 0), and the next/prev choice in the update's end-of-animation block. That block, with pNext == pB4, gives the SHOWN slot the next table id and clears its b18, which makes the loader stream in a new golfer. The comment above it ("show the next golfer of the ring") describes the code as written for more slots, so I left it.
3. fn_8008DD50 and fn_8008E468 "bNoBlend": CONFIRMED inverted. Both pass !arg to fn_8001BE88's bNoBlend and arg to GolfCamera_SwitchCrAPCamera's bBlend, so 1 = blend and 0 = cut. The callers agree: the update passes 1 at a clip's end for a smooth re-idle, and resets pass 0. For the type/param pass: rename the parameter to bBlend.
4. fn_8008E468 strcpy: CONFIRMED can overflow. The copy is strcpy(sz10, szAnim) from the caller's UNBOUNDED string, not the 32-byte bounded szName. sz10 is 0x10 bytes (camera.h:524), so a name of 16+ characters writes into sz20. Also, fn_8008E724 strncpy's into sz20[0x10] with the full size, so a 16-character name leaves sz20 unterminated. The update then passes sz20 to fn_8008E468, and strcpy runs on into sz30. EA bug, keep for matching. A port should bound the copy. The "szName != NULL" test on a local array is always true.
5. fn_8008D6CC zeroes v1C components 0, 2 and 3: CONFIRMED (the code subtracts each value from itself). Bone.v1C is f32[4], "a position" (character.h:150). It keeps component 1 (height) and zeroes x, z and w. If w is a homogeneous 1.0, zeroing it is odd. Either EA meant only x and z, or v1C is not xyzw. That is for the type pass; the code must stay. Also, the first fn_8001EED8(pModel, 0x54) result is thrown away (already noted in the source).
6. 'LITE' FourCC in fn_8008D9AC / fn_8008D9DC: CONFIRMED a multi-character constant ('CHR ' in char.c:2553/2606 too). Its value is implementation-defined in C: CodeWarrior packs it big-endian (0x4C495445). A port needs one FOURCC macro to keep the stream tags right. It is data, not an EA text that names a job, so it gives no E1 name. Also, fn_8008D9DC allocates lbl_80281EE4 on every 'LITE' object and never frees the last one (it leaks if a second one arrives).
