Findings (no code changed)
1. bBusy really means "just created, skip the header scan" (CONFIRMED). TagFile_Update sets it only when op 1 (create) succeeds. Every op other than 1/4 clears it. A plain open (op 4) then stops after the rewind (step 9) with an empty map and no scan. Re-open (op 5) clears it first. That early return (like the open/read finishes) leaves eOperation/eStep set, so a later Update without a new op returns TAG_ERROR_BUSY. Harmless for EASB, which stops polling on complete. Field name for the type pass: bJustCreated.
2. Init reads pAllocator before setting it (CONFIRMED; already noted at TagFile.c:534). TagFile_AllocBuffer gets _TagFile_pData->pAllocator from fresh, non-zeroed memory. It works on the GameCube only because TibExt's allocator ignores the heap id. A port must pass pParams->pAllocator.
3. A failed init still reads as initialised (CONFIRMED). After _TagFile_pData is allocated, every failure (checksum init, cipher init, key/map/header allocation) returns without freeing or NULLing it, and SFIO stays initialised. A retry then gets ALREADY_INITIALISED, and Shutdown runs on half-set fields (it clears and frees pHeader, which may never have been allocated). The same pattern as SFIOInit (SharedFileIO audit, Findings 4).
4. EASB image paths are dead (CONFIRMED). No code in src/ ever sets EASBState.pImageBuffer. Nothing starts op 9 (lbl_80195520: the ops started are 0,1,4,5,6,7,8 and 10), so fn_8012D030 never runs; if it did, it would index a NULL pImageBuffer. fn_8012D0D4's image branch never runs. The IMAG write steps 10 (fn_8012B0D8) and 14 (fn_8012BBD8) are in no op's step list, and the IMAG read step 7 is only in op 9. fn_8012D5E4 refuses a picture, fn_8012D7F0/fn_8012E818 are stubs, and op 7 (fn_8012D794) passes an image that its steps 8/9 never read. Also, the tag map holds 26 entries (fn_8012CAA8: 1 HEAD + 25 PROD), so 25 IMAG records could not fit anyway.
5. fn_8012D0D4 memset(pImageBuffer, 0, 0) (CONFIRMED). It clears 0 bytes and is already marked "EA bug" (untouched). It is also in the dead branch of item 4.
6. fn_8012E25C "discards the tick's return value" (REFUTED). It stores eError = fn_8012D1A0() and returns it, as fn_8012DDE0/DE38 do with eResult. The only difference: it ticks only after the product resolves. fn_8012E16C/E34C/E3C0 do not tick at all.
7. TagFile_Write with a full map (L2): TagFile_AddEntry adds nothing, yet the record is still written at uNextOffset. The call returns no error, and the record is lost on the next open. Every call after that writes to the same offset. EASB stays within 26 entries.
8. Minor (EA code, left): TagFile_Create/fn_80174DF0_Delete/Open/Reopen/End/Write/Read/GetSession have no initialised check (NULL dereference before Init). TagFile_VerifyRecord returns BAD_HEADER when the checksum result size is not 4. TagFile_Count/GetSize check pSession and never use it. fn_8012DFDC and fn_8012E084 have unreachable NULL tests. fn_8012E434 writes *puTime on INVALID_LANGUAGE. fn_8012D1A0 counts nothing until the clock passes uLastTime again after going backwards.
9. Out of unit: EASBStorage.c fn_8012C5F8's comment says "Operations 4 and 5 (fn_8012D394's)". The caller is fn_8012D560 (fn_8012D394 is init). easb.h:196 will read "(TagFile_Create)" after the rename, which is accurate.
