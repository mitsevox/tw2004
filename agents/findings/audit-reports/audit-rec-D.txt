Findings (no code changed)
1. 0x8016CFF8 in SharedFileIO.c: PLAUSIBLE, UNPROVEN. It calls only EASB (fn_8012C8D0, fn_8012C98C) and TagFile, returns EASB codes, and its only caller is EASBStorage fn_8012B27C. With 0x8016D0A8 it sits before SharedFileIO.c's first assert line (222), and nothing inside ties it to that file. It may be a separate ProDG-built EASB file (with the BMP header in .rodata 0x80186274) between CipherXOR.c and SharedFileIO.c. It is not CodeWarrior EASBStorage.c code (that is 0x8012xxxx). A split change would need a proven boundary. Left as is.
2. Device-callback names are MISLABELLED (CONFIRMED through TibExt -> MC_Gc -> CARD SDK): pfnStartProbe = mount (CARDMountAsync), pfnProbe = find the file, pfnMount = open (CARDFastOpen, returns the file number), pfnSelectDevice = unmount (CARDUnmount), pfnOp19 = close (CARDClose), pfnOp18 = stub returning 0 (TW06 has SFIO_vFlushCallback), pfn20 = create, pfn24 = delete (CARDFastDeleteAsync), pfn28 = delete by name. TW06's 17 SFIO_v*Callback names (Mount/UnMount/Open/Close/Flush/Create/Delete/Find/FreeSpace/FreeEntry/Read/Write/Seek/SetAttr/GetFile/Process ...) fit the 17 slots. Type pass. SharedFileIO.h comments are also wrong: eState "3 or 6 = idle/ready; 0xB-0xD = in progress" (0 = idle, 0xB-0xD = cleanup after a failure), uExpected54 "compared with the close result" (it is the read/write byte count), header line 4 "names with the SFIO prefix come from asserts" (only SFIOIsInitialized does). SFIO_STATE_BUSY_A/B/C should be cleanup states.
3. 0x80170E08 decodes punctuation wrong: CONFIRMED, an EA bug. For table hits it adds the range start (0x20/0x3A/0x5B/0x7B) to the table index j without subtracting the range's first index (0/16/23/29). Only ' '..'/' round-trip: ':' -> 'J', '[' -> 'r', '{' -> 0x98. Letters and digits are right. Nothing calls it or 0x80170B44, so the game is not affected. A port could add an "EA bug:" note after the audit. 0x80170B44 also reads outside its table for characters below 0x20 and 0x7F-0x80, and does not terminate its output.
4. Init/update can get stuck: CONFIRMED. (a) SFIOInit: if the second allocation fails it returns 7 with _SFIO_pDevice still allocated. SFIOIsInitialized is then TRUE, Init returns 1, and SFIOShutdown returns 2 (pData NULL), so it is stuck for good and the memory leaks. A bad device-list entry (9/0xC) after the allocations leaves both blocks and uncopied callbacks: IsInitialized is TRUE and SFIOUpdate would call an unset pfnUpdate. (b) SFIOUpdate: a validator 0x10 returns before eState/eOperation are reset, so every later start returns 0xD (busy) until Shutdown+Init. The 0xA exit resets the state but skips fn_80172FA4(0) and leaves the device mounted. A create (states 1/4) also ends without fn_80172FA4(0).
5. Knock-on names outside this unit (not changed): TagFile_BeginLoad (op 2) deletes (it calls fn_8016FBB8_DeleteStart). TagFile_Delete/TagFile_DeleteSession/TagFile_StartDelete (ops 4/5) open the file and read its tag map; EASBStorage.c:1002 already says "keeps its session and marks the file open". TagFile_BeginSave creates. ChecksumCRC32.c:21 "read directly by SharedFileIO.c" is not true in the current source. decomp-notes.md:1173 and easb.h:195 mention SFIOCreate (rename.py updates easb.h, not docs/).
6. Minor (EA code, left): 0x8016EA94 case 0x1A tests eState == 4, a create state that never reaches it. Validate slot 15 (op 0xF) uses a validator that rejects 0xF (op 0xF is never used). SFIOSeek sets uExpected54, but a seek never checks it. The delete and open starts strcpy the name into szName[0x1B] with no length check. The create start checks the length (max 25). SFIOSetDescriptor stores the descriptor before it validates it. EA's asserts call SFIOStartOp18/19's first parameter pDescriptor; SharedFileIO.h says pHandle.
