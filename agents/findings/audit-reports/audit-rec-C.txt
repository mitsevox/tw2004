audit-rec-C: LLVideo (34, the in-game movie player) + GoARAM (27, the audio-RAM heap and its DMA queue) = 61 functions. Both units are 100% matched and linked, so every behaviour below is EA's.
- Names: 34 kept (all T2), 0 renamed, 9 T3, 0 demoted, 18 unnamed (the lanes' guesses are in the ledger notes). namecheck: 9 rows, 0 errors, 0 flags.
- T3: this morning's old-style LLVideo names become fn_<ADDR>_<Name>: PreloadQueue, Stop, SetLastFrameTime, Start, IsFrameDue, UpdateAll, HasEnded, GetFrame, RunPlayback. The lanes agree on every one, but the evidence rests on our own field names.
- Tier drops, no renames: LLVideo_UpdateStream, LLVideo_ChunkAddBufferRef and LLVideo_ChunkReleaseBuffer were T1 as E3 wrappers, but their UStream callees are not audited yet. They are now T2. Every GoARAM name is supported by both lanes (T2).
- Comments: 49 ok, 9 none, 3 fixed, 0 stripped. Both unit headers are ok. The batch was simulated after the renames: each `old` occurs exactly once and no new line is over 100 characters.
- Worst: fn_800755F0's comment had bit 0 backwards ("two frames when bit 0 is clear"; it is two when bit 0 is SET). It also called the black quad a "clear". LLVideo_PlayFile's comment repeated "clearing". fn_800760A0_GetFrame said "frames decoded so far", but nFrame is 0-based (0 after the first frame). llvideo.h's field comment has the same slip; that is left for the header pass.
- Lanes: L1 misread fn_800755F0's recursion as "the opposite bit 0" (it passes bit 0 unchanged). Otherwise both lanes agreed on every body.
- Out of scope: name_sources.tsv's purpose for GoARAM_HandleTransferDone says "re-queues it", but the function releases it.
- Unclear rule: T3 guess form. I used the old name minus its unit prefix (fn_8007599C_Stop), with no object word added.

Findings (no code changed):
1. The ARAM heap never checks for running out (confirmed). GoARAM_HeapAlloc, when no free block is big enough, calls fn_800B6188 and carries on: pBest->uSize and uFree underflow and the returned address overlaps. If an exact fit takes the last free block, pFree becomes NULL and the next alloc dereferences it. GoARAM_HeapTakeBlockRecord never checks for running out of records either (500 records): with one spare left, pSpare still points at the record it hands out, so that record is later handed out again. GoARAM_QueueTransfer never checks the unused list: once all 16 transfers are in flight it dereferences NULL. GoARAM_HeapFree/fn_800B6188 dereference pUsed without a NULL check.
2. fn_800752DC_PreloadQueue can hang on a very short movie (confirmed). It loops until 16 chunks are queued and ignores the pump's return value, so a stream that ends with fewer than 16 chunks spins forever. Real movies are far longer.
3. fn_80075DEC_RunPlayback can draw with uninitialised arrays (confirmed). On the pass where the pump returns 0, it skips the update branch but still binds the picture and draws the quad (and skips fn_80006EDC, the begin-frame call). If the stream finishes before the first new frame, xy/uv were never filled.
4. fn_800760D8's TYPE note is resolved, not a bug. RenderState.uFlags (0x114, the texture source: bit 4 = pPict10C) and u110 (0x110, the dirty groups) are different fields.
5. Dead no-op pairs (confirmed). LLVideo fn_80075C48/fn_80075C68 each only call fn_80007254, an empty 4-byte stub; both call the same stub. GoARAM fn_800B655C/fn_800B6560 are empty 4-byte functions, each called once from gomainloop. Also dead: fn_800B5D08 (frees p20, which is always NULL), Video.p1018 (only ever set to NULL) and Video.b1021 (only ever 0).
6. GoARAM fn_800B6188 walks a list with no effect (confirmed). It goes once around the used list and then the free list and does nothing, and it is only reached on HeapAlloc's out-of-memory path. This is a stripped debug dump, and its comment says so accurately.
7. Other EA behaviour. fn_800754C0 has apChunk[32] but takes 1 + nMore chunks (nMore is a u8, so up to 256): nothing checks the bound. LLVideo_QueueAdd has no full-queue check (1024 slots). GoARAM_WaitTransfer would hang on an auto-release (flag 1) transfer, but every caller passes flags 0.
