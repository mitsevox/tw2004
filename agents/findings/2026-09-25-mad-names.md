# MAD decoder names: TW06 Xbox PDB and the NFSMW decomp agree (2026-09-25)

`2026-09-25-mad-names.tsv`: our `rcmp_mad_codec.c` addresses with the EA name both sources give,
in the same order. Source 1: the TW06 Xbox PDB (`Legacy_unity.obj`; file from its line table,
parameter names from its symbols). Source 2: `dbalatoni13/nfsmw` `config/GOWE69/symbols.txt`
(mangled names give the parameter types). Agreed: 14 functions and 6 globals.

Not in the TSV (only one source, or unsettled):
- `fn_800B8A2C` = `discardbits` in NFSMW's maddeca.cpp (a second static copy). TW06 has no second
  copy (inlined or shared there).
- `fn_800B8984` (the multi-byte little-endian read: realcore `getm.inl`, inlined in NFSMW) and
  `fn_800B8A04`: no name in either source.
- `madvlctbl2` / `madvlctbl3` (both 0x400 bytes) vs our `lbl_801F7258` / `lbl_801F7658`: which is
  which is not settled. 2026-09-25-ea-research.md item 1 pairs tbl2 = 7258, tbl3 = 7658 by address
  order, but our .bss is defined in reverse (the three .sbss globals come out reversed against
  NFSMW's order: madbitcount 802821B0 / madshiftreg B4 / maddataptr B8), which would make tbl2 = 7658,
  tbl3 = 7258. Check the uses in madvlcdecode before naming them.
- `idctinput` and `idctprescale` (both sources, s32[64]): not located in our file yet.

Types worth noting: TW06 declares `maddataptr` as `const u16*` (we have `u8*`, "the next coded byte")
and `MAD_initdecode`'s first parameter as `const u16* src`; `madvlctbl4` is `volatile s32[64]`.
Parameter names (TW06): `getluma(const u8* src, s32 stride, s32* dest, s32 correction)`,
`MAD_initdecode(src, motion, quality)`, `MAD_decodemacroblock(src_y, src_cb, src_cr, dest_y, dest_cb,
dest_cr, width, flags)`, `idctcompute(dest, stride)`, `dcblock(dest, stride)`, `discardbits(bits)`.
